# 3Dゲーム版 ゲームエンジン選定記録

- **決定日**：2026-10-15
- **判断**：Unity 6.3 LTS + Universal Render Pipeline（URP）を採用候補として選定し、初期制作基盤とする
- **主な実装言語**：C#
- **想定作品**：『アイラの旅』のアニメ調3D・シングルプレイヤーRPG
- **判断の性質**：初期の技術選定。性能・制作効率の実測結果によって見直す

## 1. 選定の前提

『アイラの旅』は、独立した多数の浮遊島世界と、世界ごとに異なる国・文化・制度・生態系・歴史・人物を含む巨大な作品である。

**浮遊島だから作るのが簡単なのではない。原作が巨大だから、忠実にゲーム化するとコンテンツ量と制作・管理負荷も大きくなる。**

そのため、単一シーンの最高画質や単純な描画性能だけでエンジンを選ばない。

優先する評価軸は以下の3点（相互にトレードオフがあるため、いずれか一つを絶対視しない）。

1. **開発速度**：3Dアセット、背景、アニメーション、イベント、NPCなどを効率的に制作・反復・修正できるか。アセット資産・外部ツール・自動生成・独自エディタを使いやすいか。
2. **表現品質**：求めるアニメ調のキャラクター・背景・陰影・演出を、作品全体で一貫して実現できるか。
3. **実行時の軽さ**：CPU/GPU負荷、メモリ、ロード時間、フレームタイムの安定性を制御できるか。低コストな描画表現を選択できるか。

上記と併せて、長期的なアセット管理・拡張性・制作ツールの保守コスト・ライセンス条件を確認する。

## 2. 比較した候補

| 候補 | 主な長所 | 主な懸念 | 本作における判断 |
| --- | --- | --- | --- |
| **Unity 6.3 LTS + URP** | C#、アニメ調シェーダーの構築、軽量な描画パイプライン、周辺アセット・制作ツール、非同期アセットロード | 広大な世界の構造化・自動分割は自前の設計や拡張が必要 | **開発速度・品質・軽さのバランスから第一候補** |
| **Godot 4** | 軽量な開発環境、オープンソース、柔軟な改造、3D描画の最適化手段 | 大規模コンテンツ制作・管理のために独自ツールを増やす可能性 | 軽量性重視なら有力な代替候補 |
| **Unreal Engine 5** | World Partition、HLOD、PCGなど大規模ワールド管理・生成の機能が充実 | 開発環境と制作・運用が重くなりやすい。最終的なゲーム負荷は使う機能や設定次第 | 大規模制作機能が要求を大きく上回る場合は再検討 |

この比較は**現時点の定性的な設計判断**であり、同一内容を実装して測った性能比較ではない。「Unityは常に最速・最軽量」という断定はしない。

## 3. 採用する初期技術方針

- **Unity 6.3 LTS**：制作期間中は安定したパッチ系列を基本とする。Unity公式のサポート予定は2027年12月まで（確認日：2026-10-15）。
- **URP**：アニメ調の画づくりと、必要な映像効果に合わせた描画負荷の調整を両立する。HDRP・高度なグローバルイルミネーション等の高負荷機能を前提にしない。
- **C#**：ゲームロジック、イベント、ゲームデータ、エディタ拡張・制作支援ツールに使用する。
- **Blender**：3Dモデル・アニメーション等の制作候補。具体的な制作ワークフローはプロトタイプで確立する。
- **Addressables**：後の世界追加・大規模化に備えた非同期ロードとアセット参照の候補。ただし第1弾で過剰な分割・複雑化をしない。
- **データ駆動設計**：人物・地点・イベント・世界設定を識別子やデータで整理し、描画やゲームロジックから切り離せるようにする。作者設定とゲーム都合の解釈を区別する。
- **描画最適化**：LOD、適切なカリング、インスタンシング、ライト・影・ポストプロセス負荷の制御を、実測しながら選ぶ。
- **ネットワーク**：初期構想はシングルプレイヤーであり、MMO用の認証・ゲームサーバー・永続ワールド基盤を採用条件に含めない。

「世界全体の総量」と「ある瞬間に描画・読み込みする量」は区別する。すべての世界を同時にレンダリングする設計は採らず、必要に応じてシーンや地域単位でデータを扱う。

## 4. 第1弾との関係

[第1弾](phase-1-scope.md)は、**アイラの誕生から、レスリア村で副村長を殺害して村を逃げるまで**。

全世界を同時に実装する計画ではない。最初の制作物は、原作のごく一部を完成度高く表現しつつ、後続作品の世界追加時に制作工程を流用できるかを検証する。

最初から巨大ワールドシステムを全面実装するのではなく、次を小さく検証する。

1. セルルックの人物・建物・自然物を並べ、世界観にふさわしい画づくりができるか。
2. 村の生活、時間経過、会話、イベント、演出などをデータから制作・修正できるか。
3. NPCが密集した村、背景が開けた場所、イベント演出中に安定して動くか。
4. 3Dアセットの追加・再利用・差し替えがどれほど速いか。
5. アセット数が増えても編集・ビルド・配布・ロードが管理できるか。

**第1弾の舞台が狭いことと、原作の全体規模を縮小することは異なる。** 将来の増築を阻害しない範囲で、最初は必要最小限の設計を優先する。

## 5. 検証指標・見直し条件

最初に対象プラットフォーム・代表的な実機構成・画質目標を定める。それまでは「1080pで60fps」などを確定要件としない。

プロトタイプでは少なくとも以下を記録する。

- 制作速度：モジュール式建物、NPC、イベントを1件追加・修正するのに要した時間
- 映像品質：人物と背景が同じ画風に見えるか、ライティング・影・輪郭表現の安定性
- 描画：CPU/GPUフレームタイム、ドローコール、描画・アニメーション・AIそれぞれの負荷
- メモリ：実行時メモリ使用量、シーン／アセット読み込みと解放の挙動
- 操作体験：移動・演出時のカクつきやロード停止の有無
- 開発作業：エディタの応答性、再インポート、ビルド、アセット差し替え時の運用負荷

### エンジンを再選定する条件

- 品質目標を守るための描画・ランタイム改修が過大になった
- 大量コンテンツの制作・管理がUnityの現行構成では非効率になった
- 性能目標を達成するための削減が原作表現を不当に損なう
- Unrealのワールド生成／管理機能やGodotの軽量性による利益が、移行・再制作コストを実証的に上回る

## 6. 運用上の注意

- 本書はゲーム実装の**採用判断**であり、my-memory にある原作設定の正史を更新するものではない。
- 世界観や登場人物について原典にない事柄を、ゲームエンジン都合で確定させない。
- 大規模生成・NPCシミュレーション・高度な非同期ロード等は、必要が明確になる前に作り込みすぎない。
- エンジンの採用と、画風・ゲームシステム・対象プラットフォーム・販売形態の確定を混同しない。
